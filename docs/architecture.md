# 架构与目录约定

## 边界

这是一个单一部署单元中的多应用 API 平台，不是通过查询参数分发功能的万能接口。HTTP 请求先经过平台核心，再由平台按一级路径分派给应用：

```text
client → /sw/{app}/... → platform core → registered application → response
```

应用只能拥有自己的 `/sw/{app}/**` 路由；它不应直接占用另一个应用的路径，也不应在应用之间通过 HTTP 回调来复用本地能力。需要共享的能力先由平台以显式依赖注入提供；确有跨应用的领域依赖时，应定义窄接口或事件，而不是导入对方的 HTTP router。

## 目标目录

```text
apps/
  <app-id>/
    app.toml       # 注册信息
    README.md      # 面向使用者和维护者的说明
    routes.md      # HTTP 契约
    app.py         # 未来的应用工厂（实现时新增）
    schemas.py     # 未来的请求/响应模型（实现时新增）
    services/      # 未来的领域逻辑（实现时新增）
docs/
  architecture.md
  application-contract.md
  http-conventions.md
platform/          # 未来的平台核心（实现时新增）
```

目录中未创建的 Python 文件不是遗漏：当前提交只建立架构和 API 规格，尚未提供 HTTP 运行时。

## 责任分配

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 平台核心 | 应用加载、统一身份、权限、共享依赖、限流、观测、错误和 OpenAPI 聚合 | 任何具体业务规则 |
| 应用 | 所有 `/sw/{app}/**` 路由、参数模型、领域逻辑、专属数据与说明 | 自建全局连接池、秘密读取方式、全局错误格式 |
| 基础设施适配器 | 数据库、缓存、对象存储、任务队列、外部 HTTP | HTTP 路由和领域决策 |

## 加载流程

1. 平台读取显式启用的应用清单，而不是扫描并执行任意目录。
2. 校验每个 `app.toml` 的 `id`、挂载位置、配置和能力声明。
3. 为应用提供其声明的基础设施能力。
4. 调用应用工厂，取得 router，并挂载到 `/sw/{id}`。
5. 聚合路由说明与 OpenAPI；启动失败时指出冲突的应用和原因。

路由在启动时静态确定。运行中热插拔会使 OpenAPI、鉴权和任务状态变得不可预测，不属于第一期目标。

## 何时新建一级应用

满足任一条件时，考虑从既有应用拆出新的 `{app}`：拥有独立的权限模型或数据所有权、需要独立的发布/停用节奏、对外形成稳定产品边界，或现有应用的说明已无法让使用者快速找到它。仅仅多了一个路由或工具，不是拆分理由。
